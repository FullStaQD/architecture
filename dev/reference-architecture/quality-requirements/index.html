Quality Requirements

Quality Requirements are a key aspect in designing an architecture. They describe non-functional properties of a system and must be addressed on an architectural level, as changes for addressing quality requirements can become difficult or expensive afterwards.

This section describes typical quality requirements relevant to quantum software systems in general. Although many of these quality requirements have been addressed in the design of the reference architecture, they still need to be taken into account during the implementation. Concrete quantum software systems will usually have additional quality requirements which are not covered here.

Terminology

Our quality requirements terminology is based on the arc42 quality model but tailored towards quantum software. Check out the arc42 quality docs for explanations and examples of the quality terms in the context of classical software engineering.

Adaptability

There are various different physical implementations for the mathematical model of a quantum computer. This includes neutral atom qubits, superconducting qubits and others. The field has not yet converged on a single hardware architecture and it is reasonable to assume that application developers might want to switch hardware, or be able to execute their application on multiple hardware types. Even though the physical implementation of a quantum computing device is out of scope for quantum software systems (see Context and Scope), quantum software still needs to deal with the different modalities of physical quantum device implementations such as decoherence times or qubit connectivity. We therefore specify the following quality requirement:

Quantum software systems should be adaptable to different quantum computing hardware.

Realisation in the FullStaQD Reference Architecture

In the FullStaQD Reference Architecture, adaptability is realised through the following measures:

  • The three-layered architecture specifies the Application Layer to be device-independent. This separation limits the places that need to be changed in order to adapt to a new type of quantum hardware to the System and Physical Layer.
  • Adaptation of a program to specific quantum hardware types is an explicit responsibility of the Compiler within the System Layer. Most adaptation logic can therefore be contained within a single place1, which also enables reuse of adaptation logic.

Evolvability and Extensibility

The field of quantum computing is evolving rapidly with new quantum hardware models, algorithms, error correction codes and SDKs becoming available at an enormous pace. For many of these components, it is not yet clear which exact implementations will prove to be the most useful in the realisation of practical quantum computing. To keep up with the state of the art, quantum software systems must be able to adopt such new methods. We here phrase this evolvability requirement as a matter of extensibility:

Quantum software systems need to be extensible in the following dimensions:

  • They must be extensible to use new problem transformations.
  • They must be extensible to employ new quantum algorithms.
  • They must be extensible to support new quantum programming languages and quantum SDKs.
  • They must be extensible to use new quantum error correction codes.
  • They must be extensible to use new compilation passes.
  • They must be extensible to execute quantum programs on new hardware models (see also: Adaptability).
Realisation in the FullStaQD Reference Architecture

The FullStaQD Reference Architecture realises the extensibility requirements through modularity and a clear separation of concerns.

  • New problem transformations and algorithms can be implemented as part of the Application Layer within the respective building blocks.
  • New quantum programming languages and quantum SDKs can be supported by implementing a corresponding language frontend within the System Layer's Compiler.
  • New quantum error correction codes can be implemented as compilation passes, as part of the Quantum System Controller, or as part of the Use Case within the Application Layer, see Fault Tolerance for details.
  • The compilation pass extensibility requirement is realised in the Compiler.
  • New types of quantum hardware can be supported by implementing a corresponding Common Quantum Device Interface Adapter and a corresponding Backend within the Compiler, see Adaptability.

Fault Tolerance

Quantum computers are subject to noise, i.e. their states are disturbed randomly through imprecise operations or unwanted interactions with the environment (such as electromagnetic radiation). Noise is widely recognised one of the most significant challenges in quantum computing2. When unhandled, these disturbances can accumulate such that the result of the (ideal) computation is lost. Fault tolerance is therefore one of the central quality requirements of a quantum software sytems:

Quantum software systems must be resilient to noise on hardware, i.e. quantum programs should produce their intended result even in the presence of limited amounts of noise.

Realisation in the FullStaQD Reference Architecture

The FullStaQD Reference Architecture treats Fault Tolerance as a cross-cutting concept, providing guidance on typical ways to implement fault tolerance measures such as quantum error correction, mitigation and suppression. The narrow latency and bandwidth requirements of quantum error correction are baked into the design of the architecture, see Deployment and Latency.

Integrability

Quantum computers are not expected to replace classical computers as they outperform classical computers only for problems that can be mapped well onto the quantum computation model. Therefore, quantum software systems will usually be used as part of a larger system where those specialised problems arise. For example, an optimisation problem from the scheduling systems of a logistics company might be submitted to a quantum software system, or a molecule specification from specialised pharmaceutical research software might be sent to a quantum software system for computing the ground state. Integrability is crucial for corporate users of quantum software systems, so we state the following quality requirement:

Quantum software systems must be integrable into existing IT infrastracture.

Realisation in the FullStaQD Reference Architecture

The boundaries of quantum software systems, and the integration into external IT infrastructure is discussed in the Context and Scope section. The interface between external IT systems and quantum software systems is a responsibility of the Application Layer. More specfically, the interface to external IT systems can be realised through the Use Case component, or it can be supported by specialised Integration Tooling.

Latency

Noise is one of the most significant challenges in practical quantum computing, and quantum error correction is considered a key measure in order to achieve Fault Tolerance. But as noise accumulates quickly, quantum error correction rounds must be run at a high frequence to be effective. This implies the following latency requirement:

The data transmission latency between the Quantum System Controller and the Quantum Error Correction Decoder must be low.

Realisation in the FullStaQD Reference Architecture

Latency and bandwith between execution environments are discussed in the Deployment View section. The FullStaQD Reference Architecture suggests to execute latency-critical parts of the quantum software system in an execution environment close to the QPU whereas less latency-critical parts of the system such as the compiler can be executed elsewhere. The Compiler and HPC Resource Scheduler are responsible for running latency-critical parts on suitable hardware.

Maintainability and Modularity

The key motivation behind the FullStaQD Reference Architecture is to promote interoperability in the quantum software ecosystem (see Introduction). Software engineering design principles suggest modularity as a solution to keeping complex systems maintainable. We therefore make modularity an explicit quality requirement:

Quantum software systems must be modular, i.e. changes to one component should not affect other components.

Realisation in the FullStaQD Reference Architecture

Modularity was one of the guiding design principles in the design of the FullStaQD Reference Architecture. It is achieved through a clear separation of concerns and well-defined interfaces. For example, the following architectural decisions were taken for the sake of modularity:

  • Quantum programming languages and other exchange formats act as an interface between the Application and System Layer. Changes within one of these layers will not affect the other.
  • The Common Quantum Device Interface acts as a facade to the Physical Layer. Changes to the Quantum System Controller or Simulator can therefore be contained within the Physical Layer.

See Building Block View for details.

Interchangeability

One of the key goals of the FullStaQD Reference Architecture is to promote interoperability between various components in the quantum software ecosystem. Our reference architecture describes a common framework for quantum software systems with placeholder components representing the various different responsibilities. Therefore, any component realising the full specification of some placeholder component should be suitable for an implementation. We state this as the following requirement:

All components should be interchangeable, i.e. it should be possible to substitute them with another implementation of the same type without requiring modifications to the quantum software system, or incurring loss of functionality.

Realisation in the FullStaQD Reference Architecture

The FullStaQD Reference Architecture doesn't specify concrete implementations; it merely describes the abstract components and responsibilities necessary for realising quantum software systems, as well as the interfaces between them (see Building Block View). Components of the reference architecture are therefore interchangeable by design.

Resource utilisation

In the NISQ era, quantum resources like qubits and gates will be scarce2 and resource utilisation is often a deciding factor for whether a quantum program can run at all. Major quantum hardware providers claim that devices with thousands to millions of physical qubits might become available in the next few decades but even then, practical applications might run into limits due to quantum error correction overheads or the sheer problem size. Furthermore, it is not yet clear how expensive quantum resource usage will be in the long term. Therefore, we formulate the following resource utilisation requirement:

Quantum software systems should minimise the number of used qubits and gates.

Realisation in the FullStaQD Reference Architecture

While minimising resource utilisation is a joint effort between all components of the stack, the FullStaQD Reference Architecture identifies the following key areas for achieving a low resource utilisation:

  • Application problems are first mapped to quantum programs in the Use Case and Problem Transformations components within the Application Layer. This mapping first determines the amount of required resources.
  • The Compiler within the System Layer is responsible for minimising the resource usage of a given quantum program.
  • Quantum Resource Estimation and Monitoring tools can further help analyse and understand the quantum resource usage of a given application. See the Cross-Cutting Concepts section for further details.

Scalability

NISQ era quantum hardware only features up to a few hundred qubits and gates but major hardware providers claim that these numbers will increase rapidly within the next decade. Scaling up to a large number of qubits and gates comes with new challenges: For example, decoding large quantum error correction codes can no longer be done using lookup tables, programs can no longer be stored as plain circuits and qubit routing in transpilation can become computationally expensive. We therefore state the following quality requirement:

Quantum software systems need to be scalable in terms of qubit count, gate count, and number of jobs.

Realisation in the FullStaQD Reference Architecture

The FullStaQD Reference Architecture addresses this requirement through the following measures:

  • We explore quantum program formats beyond OpenQASM circuits. Since no standard has yet emerged for this purpose, the interfaces between the three layers deliberately allow for different formats and components are specified with dynamic circuits in mind. See the Building Block View section for further details.
  • The Deployment View section also discusses the integration of QPUs into HPC systems to meet computational needs. For example, the architecture suggests to locate QEC decoders on powerful machines close to the Quantum System Controller.
  • The architecture addresses the potentially large number of quantum computing jobs through an integration with HPC resource schedulers. See the Physical Layer for details.

In the end, however, scalability is something that cannot be addressed in the architecture alone and needs to be considered in the design of individual components too.

Unit Testability

The FullStaQD Reference Architecture aims to achieve a separation of concerns that allows vendors to implement quantum software components independently from each other. The Modularity requirement already states that changes to one component should not affect other components. For full independence of the development process, developers also need to be able to test components independently from each other. We therefore state the following unit testability requirement:

Components of quantum software systems should be testable independently from each other.

Realisation in the FullStaQD Reference Architecture

The FullStaQD Reference Architecture discusses benchmarking and testing tools as Cross-Cutting Concepts.
